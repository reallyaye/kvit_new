# Реестр ошибок и строгих инженерных правил (MISTAKES.MD)

> **КРИТИЧЕСКОЕ ПРАВИЛО ДЛЯ АГЕНТА:**
> Перед началом выполнения любых задач, связанных с Docker, авторизацией, базами данных, веб-сервером или файловой структурой, **ОБЯЗАТЕЛЬНО ПРОЧИТАЙ ЭТОТ ФАЙЛ** и строго соблюдай все зафиксированные в нём уроки. Повторение зафиксированных ошибок строго запрещено!

## 1. Docker & Dockerfile синхронизация файлов
- **Симптом ошибки:** `python: can't open file '/app/...': [Errno 2] No such file or directory` при вызове `docker compose exec kvit-api python script.py`.
- **Причина:** В `Dockerfile` инструкция `COPY` перечисляла файлы поштучно. При создании нового скрипта (например, `import_accounts.py`, `set_password.py`, `accounts_all.xlsx`) он не попадал в Docker-образ без обновления `Dockerfile` и пересборки.
- **Железное правило:** 
  1. При создании любого нового исполняемого скрипта или ресурса в проекте — **СРАЗУ ЖЕ** проверять `Dockerfile` и `.dockerignore`, чтобы файл гарантированно копировался внутрь контейнера.
  2. Если пользователю нужно выполнить скрипт внутри контейнера, напоминать о необходимости пересборки (`docker compose up -d --build`).

## 2. Docker Compose и синтаксис переменных (`$`)
- **Симптом ошибки:** Предупреждение `WARN The "..." variable is not set. Defaulting to a blank string` и обрезанный парольный хеш.
- **Причина:** Docker Compose воспринимает символы `$` (например, в PBKDF2 хешах `pbkdf2_sha256$600000$...`) как попытку интерполяции переменных окружения.
- **Железное правило:**
  1. **НИКОГДА** не хардкодить строки со знаками `$` внутри `docker-compose.yml` без двойного экранирования `$$`.
  2. Дефолтные fallback-значения хешей и паролей должны определяться на уровне Python-кода (`config.py`), а не в `docker-compose.yml`.

---

## 3. Cookie, сессии и HTTP/HTTPS окружения
- **Симптом ошибки:** Пользователь вводит верный пароль, форма отправляется, но вход не происходит (пользователь остаётся неавторизованным).
- **Причина:** Сервер выставлял атрибут `; Secure` в заголовке `Set-Cookie` только на основе `APP_ENV=production`. Браузеры (Chrome, Edge, Firefox, Safari) по стандартам безопасности RFC **молча отклоняют** `Secure` cookies, если страница открыта по незащищённому протоколу HTTP (например, `http://localhost:8080` на виртуалке).
- **Железное правило:**
  1. Флаг `Secure` для cookie должен выставляться **ТОЛЬКО** при реальном HTTPS-соединении (проверка `X-Forwarded-Proto: https` или прямого TLS).
  2. Для cookie сессии использовать `SameSite=Strict` или `SameSite=Lax`, гарантируя корректное сохранение токена при HTTP 302/303 редиректах.

## 4. Диалекты SQL: SQLite vs PostgreSQL
- **Симптом ошибки:** `syntax error at or near "OR"` при выполнении скриптов импорта на PostgreSQL.
- **Причина:** Использование специфичного для SQLite синтаксиса `INSERT OR REPLACE INTO ...`.
- **Железное правило:**
  1. Во всех скриптах и запросах, работающих с базой, использовать исключительно стандартный и кроссплатформенный синтаксис: `INSERT INTO ... ON CONFLICT (...) DO UPDATE SET ...` или `DO NOTHING`.

## 5. Имена файлов и кроссплатформенность
- **Симптом ошибки:** Проблемы с кодировками (UTF-8 vs CP1251 vs ASCII), битые символы `` при передаче файлов между Windows и Linux (Debian).
- **Железное правило:**
  1. Все файлы проекта, скрипты, статика и таблицы должны именоваться строго на **английском языке (латиница + ASCII)**: `accounts_all.xlsx`, `set_password.py` и т.д. Без пробелов и кириллицы.

## 6. Чувствительность к регистру строк в PostgreSQL (Case-Sensitivity)
- **Симптом ошибки:** Квитанция загружена и распознана (бот пишет `дубликат (уже в базе)`), но при поиске по счёту сайт и бот пишут: `Квитанции для данного счёта ещё не загружены`.
- **Причина:** В SQLite строки `'ready'` и `'READY'` в некоторых фильтрах равны, а в PostgreSQL сравнение строк строго чувствительно к регистру (`'ready' != 'READY'`). При записи статуса в нижнем регистре `ready`, запрос `WHERE status = 'READY'` возвращал 0 записей.
- **Железное правило:**
  1. Все строковые статусы сущностей (`READY`, `MISSING`, `PROCESSING`, `FAILED`, `PENDING`, `APPROVED`, `REJECTED`) должны храниться строго в **ВЕРХНЕМ РЕГИСТРЕ (UPPER_CASE)**.
  2. Во всех SQL-запросах фильтрации использовать регистронезависимое сравнение: `(UPPER(status) = 'READY' OR status IS NULL OR status = '')`.

## 7. Изоляция файловой системы между Docker контейнерами (Shared Spool Volume)
- **Симптом ошибки:** `FileNotFoundError: No such file or directory: '/tmp/kvit_tg_upload_...' -> '/app/data/processing/...'` в `kvit-worker`.
- **Причина:** Контейнер `kvit-api` (бот/веб) сохранял входящие файлы в системный `/tmp`, который изолирован внутри контейнера API и невидим для контейнера `kvit-worker`.
- **Железное правило:**
  1. Любые входящие файлы, передаваемые в очередь фоновых задач (`TaskManager`), должны создаваться **СТРОГО** внутри общего смонтированного тома `config.SPOOL_DIR` (`dir=config.SPOOL_DIR`), а не в системном `/tmp`.

## 8. Переменные окружения для воркеров (Worker Environment)
- **Симптом ошибки:** Воркер завершил задачу, но отчёт в Telegram не пришёл.
- **Причина:** В `docker-compose.yml` у сервиса `kvit-worker` отсутствовала переменная `TELEGRAM_BOT_TOKEN`, из-за чего воркер не мог отправить HTTP-запрос в Telegram API.
- **Железное правило:**
  1. Все переменные интеграций (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_IDS`, `SECRET_KEY`) должны передаваться во все контейнеры, взаимодействующие с внешними API (`kvit-api`, `kvit-worker`).

- **Железное правило:**
  1. При тестировании боевого сайта `https://krec.kz` использовать прямой сетевой бенчмарк (Python `urllib`/`requests`/`socket`/`ssl` или `curl`/системный Chrome) с замером TTFB, TLS, заголовков и WebSocket рукопожатия, не полагаясь на динамическую загрузку внешних zip-драйверов.

  2. Всегда сначала проверять текущую реализацию и отталкиваться исключительно от реальных пробелов в коде.

## 12. Режим техобслуживания при работах на боевом сервере (Maintenance Mode)
- **Причина:** При проведении любых обновлений, миграций или работ на боевом сервере пользователи не должны видеть ошибки (502/500/сломанную верстку).
- **Железное правило:**
  1. Перед любыми работами на проде ОБЯЗАТЕЛЬНО активируется страница плановых технических работ (`maintenance.html` / `503 Service Unavailable`).
  2. Страница снимается только после завершения всех миграций, полного тестирования и подтверждения работоспособности.

## 13. Автоматическое применение миграций PostgreSQL и валидация схемы перед запуском
- **Симптом ошибки:** `column "username" does not exist` в PostgreSQL после добавления новых колонок в схему, из-за чего сессия не читается и пользователя циклически перенаправляет обратно на `/login`.
- **Причина:** Использование `CREATE TABLE IF NOT EXISTS` не добавляет новые колонки в уже существующие таблицы в PostgreSQL, а пакетное выполнение SQL-скрипта через psycopg2 может прерываться или пропускать DDL-инструкции `ALTER TABLE`.
- **Железное правило:**
  1. При добавлении любых новых полей в таблицы — **ВСЕГДА** явно прописывать `ALTER TABLE <таблица> ADD COLUMN IF NOT EXISTS <колонка> <тип>` и в `schema.postgres.sql`, и непосредственно в процедуру `migrate_db()`.
  2. Все DDL инструкции для PostgreSQL должны выполняться **построчно/пооператорно (`statement-by-statement`)** с изолированной обработкой ошибок.
  3. После любого деплоя с изменениями схемы БД **ОБЯЗАТЕЛЬНО проверять логи контейнера (`docker logs kvit-api`) на отсутствие SQL-ошибок** перед снятием флага Maintenance Mode.

## 14. Гарантированное снятие флага техобслуживания и верификация боевого ответа (HTTP 200 vs 503)
- **Симптом ошибки:** После завершения работ сайт остаётся на заглушке «Ведутся технические работы» (503 Service Unavailable), так как файл `data/maintenance.flag` остался на сервере.
- **Причина:** Команда удаления `rm -f data/maintenance.flag` была объединена в цепочку с другими командами деплоя (перезапуск Docker, git pull), и при ненулевом коде возврата промежуточной команды завершающая команда удаления не выполнилась.
- **Железное правило:**
  1. Удаление флага `data/maintenance.flag` **ВСЕГДА выполняется отдельной независимой командой**.
  2. **НИКОГДА не рапортовать пользователю о готовности**, пока не выполнен финальный `curl -k -I https://127.0.0.1/` и не получен фактический код **`HTTP/2 200 OK`** (убедиться, что возвращается не 503 и не страница техобслуживания).
  3. Обязательно проверять отсутствие файла `data/maintenance.flag` на диске сервера.

## 15. Пересборка Docker-образов при изменении исходного кода (`docker compose build`) и оптимизация `.dockerignore`
- **Симптом ошибки:** После `git pull` и `docker compose restart kvit-api` сервер продолжал работать на старой версии кода, а попытка `docker compose build` зависала или передавала контекст размером 3.4 ГБ из-за неучтённых поддиректорий данных (`data/receipts/`, `data/uploads/` и т.д.).
- **Причина:** 
  1. В `Dockerfile` исходный код копируется внутрь образа (`COPY . /app`). Простой `restart` контейнера не обновляет запечённые в образ файлы Python.
  2. В `.dockerignore` отсутствовали исключения для директорий с боевыми PDF-квитанциями и логами внутри папки `data/`.
- **Железное правило:**
  1. При любых изменениях исходного кода приложения (`server.py`, `migrations.py`, `templates/`, `services/`) на боевом сервере **ОБЯЗАТЕЛЬНО выполнять явную пересборку**: `docker compose build kvit-api kvit-worker && docker compose up -d kvit-api kvit-worker`.
  2. В `.dockerignore` **ВСЕГДА** должны быть исключены все тяжелые каталоги данных и логов (`data/receipts/`, `data/uploads/`, `data/certbot/`, `data/nginx-logs/`, `data/api-logs/`, `data/worker-logs/`, `data/processing/`, `data/spool/`, `data/failed/`), чтобы контекст сборки передавался мгновенно (< 1 МБ).
  3. После перезапуска сервисов выполнить верификационный запрос `POST /login` и проверить успешный ответ `HTTP 302/200` в логах контейнера.

## 17. Строгий запрет на смайлики и эмодзи в интерфейсе (No Emojis Policy)
- **Причина:** Текстовые смайлики и эмодзи (`👥`, `📥`, `❌`, `✅`, `👑`, `💼`, `↗️` и т.д.) нарушают строгий корпоративный дизайн, по-разному отображаются на разных ОС (Windows/Linux/iOS/Android) и выглядят непрофессионально.
- **Железное правило:**
  1. **НИКОГДА** не использовать текстовые эмодзи и смайлики в интерфейсе (кнопки, вкладки, бейджи, селекторы, статусы, заголовки, алерты).
  2. Для любых визуальных акцентов использовать **ТОЛЬКО векторные SVG-иконки** из модуля `templates/icons.py` (`icon(name, size, color)`).
  3. Все иконки должны быть согласованы по стилю (Lucide / Feather style: stroke-width 1.5–2px, чистые геометрические формы).

## 18. Полнота выдачи данных в Telegram-боте (мультипериодная выдача квитанций)
- **Симптом ошибки:** На сайте квитанции отображаются за все месяцы (2+ периода), а в Telegram-боте отправляется только 1 файл за последний месяц.
- **Причина:** Логика выдачи брала `receipts[0]` вместо итерации по всему списку `receipts`.
- **Железное правило:**
  1. При поиске по лицевому счету или адресу в Telegram-боте **ВСЕГДА** отправлять все найденные квитанции за все периоды в цикле (`for rec in receipts:`).
  2. В unit-тестах Telegram-бота (`test_telegram_bot.py`) обязательно проверять мультипериодную выдачу (минимум 2 квитанции за разные месяцы).

## 19. Строгая типизация в PostgreSQL (`BOOLEAN` vs `INTEGER`) и изоляция HTTP-ошибок (No 502 Bad Gateway)
- **Симптом ошибки:** При отправке формы создания пользователя (`POST /admin/users/create`) возвращается `502 Bad Gateway` от Nginx.
- **Причина:**
  1. В PostgreSQL колонка `is_active` имеет тип `BOOLEAN`. Передача целочисленного значения `1` вместо Python `True` вызывает ошибку `psycopg2.errors.DatatypeMismatch`.
  2. Обработчик запроса перехватывал только `ValueError`, из-за чего необработанное исключение БД роняло воркер.
- **Железное правило:**
  1. Для `BOOLEAN` колонок в SQL-запросах передавать строго булевы значения `True` / `False` или `bool(...)`, корректно обрабатываемые и SQLite, и PostgreSQL.
  2. Во всех HTTP POST/GET обработчиках в `server.py` **ОБЯЗАТЕЛЬНО** оборачивать логику в `try...except Exception as e` с логированием в `logger.error` и безопасным возвратом/редиректом с URL-экранированием (`urllib.parse.quote`), чтобы ни одна ошибка приложения не приводила к `502 Bad Gateway`.

## 21. Синхронизация `PROTECTED_PATHS` и префиксов `/admin` при добавлении новых страниц админки (No 404 for admin routes)
- **Симптом ошибки:** При переходе по ссылке на новый раздел админ-панели (например `/admin/audit`) сервер отображал страницу 404 «Страница не найдена».
- **Причина:** В `server.py` маршрутизация авторизованной зоны производилась строго по списку `elif path in PROTECTED_PATHS:`. Если новый путь отсутствовал в `PROTECTED_PATHS` (`config.py`), запрос проваливался в обработчик CMS и пытался найти страницу сайта со слагом `'admin/audit'`.
- **Железное правило:**
  1. Любой новый эндпоинт админ-зоны **ОБЯЗАТЕЛЬНО** должен вноситься в `PROTECTED_PATHS` в `config.py`.
  2. В `server.py` роутер авторизации обязан поддерживать как точное совпадение с `PROTECTED_PATHS`, так и общий префикс `path.startswith('/admin')`, гарантируя, что ни один внутренний маршрут панели управления не провалится в 404 CMS.

## 22. Абсолютный запрет на использование эмодзи — строго векторные SVG-иконки (Strictly SVG Icons, Zero Emojis)
- **Симптом ошибки:** В интерфейсе сайта, плашках адресов, переключателях языка или кнопках появлялись эмодзи (например 📍, 🇰🇿, 🇷🇺, ✕, 🏢).
- **Причина:** Использование символов эмодзи Unicode вместо стандартизированных SVG-иконок из `templates/icons.py`.
- **Железное правило:**
  1. **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** использовать любые эмодзи (Unicode emoji) и спецсимволы в интерфейсе, кнопках, формах, модальных окнах, карточках и статических страницах портала.
  2. Все пиктограммы оформляются **СТРОГО** через векторные SVG-иконки (`icon('name', size, color)` или инлайн-SVG с классами `svg-icon-stroke`).
  3. Для языковых переключателей использовать чистый лаконичный текст («Қазақша», «Русский») без флажков.

## 23. Исключение ложной кликабельности (No False Affordance on Static Elements)
- **Симптом ошибки:** При наведении курсора на некликабельные элементы (плашки адресов, списки документов, информационные чипы) срабатывала анимация поднятия карточки и подсветка (`transform: translateY(-1px)`, смена фона на синий), создавая ложное ощущение, что на элемент можно нажать.
- **Причина:** Назначение интерактивных стилей `:hover` (кнопочных эффектов) чисто статическим информационным блокам.
- **Железное правило:**
  1. **ЗАПРЕЩЕНО** вешать анимации смещения (`translateY`), подпрыгивания и активной подсветки на некликабельные информационные блоки, бейджи и чипы адресов.
  2. Анимация наведения (`:hover`) допустима **ТОЛЬКО** для ссылок (`<a>`), кнопок (`<button>`) и элементов с реальным обработчиком клика.
  3. Для статических информационных блоков явно указывать `cursor: default;` и сохранять нейтральное оформление.
